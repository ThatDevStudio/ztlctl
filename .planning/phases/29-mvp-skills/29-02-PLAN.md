**Body** (~120-180 lines):
1. H1: "Session Lifecycle"
2. Opening paragraph: "Sessions are the primary coordination unit in ztlctl. This skill manages the full arc: pre-flight check, polaris alignment, start, and close with enrichment. Detect which path to run from the user's intent — 'start/begin/open' runs the open path; 'close/end/finish' runs the close path."
3. H2: "Iron Laws" (bold, at top):
   - "**Check `result.success` after every MCP call.** If session_start or session_close fails, stop and surface the error."
   - "**Only one session can be open at a time.** If a session is already open when the user asks to start, present the active session and ask: close it first, or reuse it?"
4. H2: "Open Path" — numbered steps:
   - Step 1: `session_status()` — check if a session is already open
     - If open: surface the active session ID, topic, and start time. Ask user: "Session <ID> is open on '<topic>'. Close it first, or continue with it?"
     - If no session open: proceed to step 2
   - Step 2: Read `ztlctl://polaris` — load current priorities
   - Step 3: `check_alignment(decision="Open session: <topic>")` — advisory alignment check; report which priorities this session relates to
   - Step 4: `session_start(topic="<topic>")` — open session; capture the returned session ID
   - Step 5: Read `ztlctl://self/methodology` — load vault workflow conventions for this session
   - Step 6: Report to user: session ID, aligned polaris priorities, methodology summary. "Session <ID> is now open. Relevant priorities: [list]. Ready to capture."
5. H2: "Close Path" — numbered steps:
   - Step 1: Ask user for a session summary if not provided (one sentence describing what was accomplished)
   - Step 2: `session_close(summary="<summary>")` — close session; receive enrichment report
   - Step 3: Parse enrichment report and present: reweave_count (notes rewoven), orphan_count (orphans found and linked), integrity_issues (broken links or missing files found)
   - Step 4: If integrity_issues > 0: warn user: "Found [N] integrity issues during enrichment. Consider running `ztlctl check check` for details."
6. H2: "Path Detection" — explain how to determine which path:
   - Open path triggers: "start", "begin", "open", "new session", "work on X"
   - Close path triggers: "close", "end", "finish", "wrap up", "done with session"
   - Ambiguous: ask user "Do you want to start a new session or close the current one?"
7. Footer: "See `references/session-lifecycle.md` for the full session state machine. See `references/enrichment-report.md` for interpreting enrichment pipeline output."

Create `plugin/skills/review-triage/SKILL.md` with the following structure and content:

**Frontmatter** (YAML between `---` markers):
- `name: review-triage`
- `description: >` followed by: "Use when the user asks to review the work queue, triage pending items, clear the backlog, or find out what needs attention in the vault. Surfaces prioritized actionable items and batch-processes approved updates."
- `version: 1.0.0`
- `disable-model-invocation: true` (write side-effects: update_content and close_content modify vault state)

**Body** (~100-150 lines):
1. H1: "Work Queue Review and Triage"
2. Opening paragraph: "Review the vault's work queue, evaluate each item, and batch-process approved actions. This skill uses the loop pattern: enumerate all items, inspect each, propose actions, then execute approved set after user confirmation."
3. H2: "Iron Laws" (bold, at top):
   - "**Never write without confirmation.** Present the full proposed action set BEFORE executing any writes. The user approves or prunes the batch."
   - "**Check `result.success` after every write.** If update_content or close_content fails, stop the batch and report what succeeded and what failed."
4. H2: "Workflow" with numbered steps:
   - Step 1: `work_queue()` — load the prioritized work queue (all actionable items with scores)
   - Step 2: For the top items (up to 10): `get_document(content_id="<id>")` — fetch full content to evaluate
   - Step 3: Evaluate each item — classify as:
     - **Stale seed**: created > 7 days ago, maturity=seed, no updates -> suggest: promote to budding or archive
     - **Actionable task**: has clear next step -> suggest: keep as-is or mark complete
     - **Orphan note**: 0 outgoing links -> suggest: add links via reweave or archive
     - **Draft needing attention**: draft status, has content but no connections -> suggest: add tags/links to promote
   - Step 4: Present summary table to user:
     ```
     | # | ID | Title | Type | Suggestion | Priority |
     ```
     Ask: "Process all / only high-priority (score > X) / pick specific items?"
   - Step 5: For approved items, execute in batch:
     - Promote: `update_content(content_id="<id>", changes={maturity: "budding"})` or status transition
     - Archive: `close_content(content_id="<id>")`
     - Reweave: `reweave(content_id="<id>")` for orphan connection
   - Step 6: Report: items reviewed, items updated, items archived, items remaining in queue
5. H2: "Batch Confirmation Pattern" — explain the interaction model:
   - Always present proposed actions before executing
   - User can select "all", "high-priority only", or cherry-pick specific items
   - Archives are highlighted separately (irreversible soft-delete)
   - After batch: report successes and failures
6. Footer: "See `references/triage-workflow.md` for item evaluation criteria and priority scoring details."

**Create `plugin/skills/review-triage/references/triage-workflow.md`** (~60-80 lines):
1. H1: "Triage Workflow Reference"
2. H2: "Work Queue Scoring" — explain how items are scored:
   - Work queue returns items sorted by composite score
   - Score considers: time since creation, link count, maturity stage, update recency
   - Higher score = more urgent attention needed
3. H2: "Evaluation Criteria" — expanded classification:
   - Stale seeds: maturity=seed, age > 7 days, no body updates -> low effort to promote or archive
   - Orphan notes: 0 outgoing links, status=draft -> need connections; reweave may help
   - Completed tasks: all subtasks done or marked complete -> archive candidate
   - Decision notes in draft: need acceptance or rejection
4. H2: "Batch vs Individual Processing" — when to use each:
   - Batch: when the queue has many similar items (e.g., 10 stale seeds) -> process all at once
   - Individual: when items need different evaluations (e.g., mix of tasks and notes) -> present each
   - Default to batch with user confirmation gate
5. H2: "Status Transitions" — reference the valid transitions:
   - seed -> budding -> evergreen (maturity progression)
   - draft -> linked -> connected (note status, computed from link count)
   - active -> archived (soft-delete, preserves edges)
