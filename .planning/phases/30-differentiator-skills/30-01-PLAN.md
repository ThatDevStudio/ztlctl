ztl:decision-support (structured decision analysis), and ztl:orient-session
(recall-driven session start). Each skill gets a SKILL.md and one reference file.

through raw MCP calls — synthesis requires a 7-step pipeline, decision support

require temporal and topic recall before starting.

    **ztl:synthesize** (SKIL-06):
    - Frontmatter: name=synthesize, description mentioning "synthesize", "connect
      notes", "consolidate knowledge", "find gaps". Version 1.0.0.
      disable-model-invocation: true.
    - Description must use unique verbs: "synthesize", "connect", "consolidate" —
      NOT "review", "capture", "orient" (those belong to other skills).
    - Iron Laws: (1) Always search before synthesizing — check what exists.
      (2) Present draft to user before creating note — never auto-write synthesis.
      (3) Check result.success after every MCP call.
    - Workflow (7 steps from FEATURES.md section 7):
      1. search(query="<topic>", limit=20) — survey existing content
      2. graph_gaps(top=10) — find structural isolation in knowledge graph
      3. topic_packet(topic="<topic>", mode="learn") — comprehensive topic context
      4. If no mature synthesis exists: draft_from_topic(topic="<topic>", target="note")
      5. Present draft to user for approval/modification (checkpoint)
      6. create_note(title="<synthesis title>", body="<approved draft>", tags=["<topic>"])
      7. Report: note ID, connected notes, gaps surfaced, bridge candidates
    - "When NOT to use" section (like orient skill)
    - Reference link: See references/synthesis-workflow.md

    **ztl:decision-support** (SKIL-07):
    - Frontmatter: name=decision-support, description mentioning "decide",
      "evaluate options", "decision briefing", "decision context".
      Version 1.0.0. disable-model-invocation: true.
    - Description must use unique verbs: "decide", "evaluate" — NOT "align" or
      "check priority" (those belong to ztl:align).
    - Iron Laws: (1) Read-only by default — present briefing, never auto-create
      decision notes. (2) Check result.success after every MCP call.
    - Workflow (6 steps from FEATURES.md section 10):
      1. decision_support(topic="<topic>") — aggregate relevant decisions/tasks/refs
      2. Read ztlctl://decision-queue — recent decisions plus active work queue
      3. Read ztlctl://polaris — current priorities
      4. check_alignment(decision="<proposed decision>") — advisory polaris check
      5. topic_packet(topic="<topic>", mode="decision") — supporting/conflicting links
      6. Synthesize and present structured briefing: prior decisions, conflicting
         signals, polaris alignment, recommended action
    - Optional decision note creation (only on explicit user request):
      create_note(title="Decision: <title>", subtype="decision", body="...")
    - Distinction from ztl:align: align is a quick pass/fail priority check;
      decision-support is a comprehensive briefing assembling multiple data sources.
    - Reference link: See references/decision-workflow.md

    **ztl:orient-session** (SKIL-08):
    - Frontmatter: name=orient-session, description mentioning "recall", "resume",
      "continue work", "pick up where I left off". Version 1.0.0.
      disable-model-invocation: true.
    - Description must use unique verbs: "recall", "resume", "continue" — NOT
      "start session" (that belongs to ztl:session) or "orient" (ztl:orient).
    - Iron Laws: (1) Present prior context summary before opening session — never
      start a recall session without showing what was found. (2) Check result.success
      after every MCP call.
    - Workflow (6 steps from FEATURES.md section 5):
      1. Read ztlctl://sessions/recent — scan last 5 sessions for relevance
      2. recall_topic(query="<topic>") — find sessions with matching log entries
      3. For relevant sessions: extract note_ids, call get_document on key notes
      4. Summarize: "Found N prior sessions on this topic. Key notes: [list]."
      5. Present summary and ask user to confirm continuation (checkpoint)
      6. session_start(topic="<topic> — continued") — start grounded in prior context
    - Path detection: same pattern as ztl:session — explain that this skill is for
      RESUMING prior work, not for cold-start sessions (use ztl:session for that).
    - Reference link: See references/recall-workflow.md

    **Style constraints (from Phase 29 analysis):**
    - Keep each SKILL.md between 55-75 lines (matching MVP skill range)
    - Use ## headings for major sections (Workflow, Iron Laws, When NOT to use, etc.)
    - Numbered workflow steps with bold tool name first, then em-dash, then explanation
    - Reference existing patterns: Iron Laws from session/review-triage, When NOT to use from orient
    - Do NOT inline MCP tool signatures or parameter schemas — Claude already has those from MCP discovery
    - Do NOT duplicate agentic-workflows.md content — reference it, don't copy it

    reference files. Reference files provide progressive disclosure — detailed
    implementation guidance that SKILL.md links to but does not inline.

    **synthesis-workflow.md** (reference for ztl:synthesize):
    - Document the graph_gaps output format: what "structural isolation" means,
      how gap scores work, what top=10 returns
    - Document the topic_packet output format: what mode="learn" returns vs
      mode="decision", what the "gaps", "bridges", "stale" fields contain
    - Document the draft_from_topic output: what the draft payload looks like,
      what target="note" vs target="reference" means
    - Document the checkpoint pattern: how to present the draft for user approval,
      what modifications the user can make (title, body, tags)
    - Document empty results handling: what to do when search returns 0 results
      (the topic is new to the vault), when graph_gaps returns no isolation
    - Approximately 40-60 lines matching existing reference file depth

    **decision-workflow.md** (reference for ztl:decision-support):
    - Document the decision_support output format: what fields it returns
      (relevant decisions, tasks, references, scoring)
    - Document the ztlctl://decision-queue resource: what it contains (recent
      decisions plus active work queue items), how it differs from work_queue()
    - Document mode="decision" in topic_packet: how it differs from mode="learn",
      what supporting/conflicting links look like
    - Document the briefing format: how to structure the final synthesis
      (prior decisions, conflicting signals, polaris alignment, recommendation)
    - Document distinction from ztl:align: align is a quick yes/no priority check;
      decision-support is a comprehensive multi-source briefing
    - Document optional decision note creation: subtype="decision" parameter,
      when to suggest it (only on explicit user request)
    - Approximately 40-60 lines

    **recall-workflow.md** (reference for ztl:orient-session):
    - Document the ztlctl://sessions/recent resource: what it returns (last N
      sessions with IDs, topics, timestamps, note counts)
    - Document recall_topic output: what query matching looks like, how session
      log entries are searched, what "relevance" means in this context
    - Document the get_document calls: why we fetch key notes from prior sessions
      (to rebuild context), how to select which notes to fetch (highest-scored,
      most recently modified)
    - Document the continuation pattern: why topic gets " — continued" suffix
      (creates a session lineage), how the new session relates to prior ones
    - Document empty results handling: no prior sessions found (cold start —
      suggest ztl:session instead), topic not found in any session
    - Approximately 40-60 lines

    **Style constraints (from Phase 29 reference files):**
    - Title as H1 heading
    - Brief intro paragraph explaining what this reference covers
    - H2 sections for each major concept
    - Concrete parameter values and output field names — this is reference material
    - No workflow steps (those live in SKILL.md) — this is supplementary detail
