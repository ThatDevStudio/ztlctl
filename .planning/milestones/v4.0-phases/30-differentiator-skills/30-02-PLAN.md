    **ztl:garden-health** (SKIL-09):
    - Frontmatter: name=garden-health, description mentioning "garden", "maintain",
      "vault health", "orphan sweep", "what is stale". Version 1.0.0.
      disable-model-invocation: true.
    - Description must use unique verbs: "garden", "maintain", "health" — NOT
      "review" or "triage" (those belong to ztl:review-triage).
    - Iron Laws: (1) Audit first, act second — complete the full analysis before
      proposing any remediation. (2) Never remediate without confirmation — present
      the full maintenance report and wait for user approval before any writes.
      (3) Check result.success after every MCP call.
    - Workflow (Fan-Out pattern from FEATURES.md section 9):
      1. Read ztlctl://garden/backlog — stale seeds and orphan notes
      2. Read ztlctl://review/dashboard — external review workbench snapshot
      3. vault_review() — comprehensive aggregate snapshot (stale count, orphan count,
         maturity distribution)
      4. graph_gaps(top=10) — structurally isolated clusters
      5. graph_bridges(top=10) — high-value bridge nodes at risk
      6. Synthesize health report: orphans, stale seeds, structural gaps, bridge risks
      7. Present prioritized action list with confirmation gate: connect orphans (reweave),
         promote stale seeds, document gaps. Ask: "Process all / select specific items?"
    - Distinction from ztl:review-triage: review-triage focuses on the work queue
      (actionable items); garden-health focuses on structural vault health (orphans,
      gaps, bridges, staleness).
    - Reference link: See references/garden-audit.md

    **ztl:review-contradictions** (SKIL-10):
    - Frontmatter: name=review-contradictions, description mentioning "contradict",
      "review conflicts", "inconsistencies", "conflicting notes". Version 1.0.0.
      disable-model-invocation: true.
    - Description must use unique verbs: "contradict", "conflicts", "inconsistencies"
      — NOT "review" without qualification (belongs to ztl:review-triage).
    - Iron Laws: (1) NEVER auto-confirm contradictions — each pair requires explicit
      user approval before confirm_contradiction fires. Contradictions insert
      permanent bidirectional graph edges. (2) Gracefully degrade if sqlite-vec is
      absent — fall back to heuristic scoring, do not error out. (3) Check
      result.success after every MCP call.
    - Workflow (Loop pattern from FEATURES.md section 8):
      1. Read ztlctl://review/contradictions — load current candidate list
      2. If no candidates: run check_contradictions(max_pairs=20) to generate fresh
      3. For each candidate pair (score > 0.5):
         a. get_document(content_id="<note_a>") and get_document(content_id="<note_b>")
         b. Evaluate: do the notes genuinely contradict? Check signals field
         c. Present pair with proposed verdict: "Genuine contradiction" or "False positive"
      4. Wait for user to approve/reject each verdict (per-pair checkpoint)
      5. For confirmed contradictions: confirm_contradiction(note_a="<a>", note_b="<b>")
      6. Report: pairs reviewed, genuine contradictions confirmed, false positives dismissed
    - Graceful degradation note: if check_contradictions returns an error mentioning
      sqlite-vec, surface: "Semantic contradiction detection requires sqlite-vec.
      Install with: uv add sqlite-vec. Falling back to heuristic scoring."
    - Reference link: See references/contradiction-review.md

    - Reference existing patterns: Iron Laws from session/review-triage,
