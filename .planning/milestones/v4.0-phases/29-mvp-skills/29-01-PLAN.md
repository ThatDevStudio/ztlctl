Create `plugin/skills/capture/SKILL.md` with the following structure and content:

**Frontmatter** (YAML between `---` markers):
- `name: capture`
- `description: >` followed by: "Use when the user wants to capture research, create a note about a topic, ingest an external source, or add knowledge to the vault. Guides structured content creation with duplicate detection and automatic linking."
- `version: 1.0.0`
- `disable-model-invocation: true` (write side-effects: creates notes and references)

**Body** (~80-120 lines):
1. H1: "Research Capture"
2. Opening paragraph: "Capture knowledge into the vault with duplicate detection, proper metadata, and automatic linking. This skill encodes the research capture recipe: search first, then create."
3. H2: "Iron Law" (bold, top of body):
   - "**Always search before creating.** Duplicates waste effort and fragment knowledge. Step 1 is non-negotiable."
   - "**Check `result.success` after every write.** If a create or ingest call fails, stop and surface the error — do not proceed to the next step."
4. H2: "Workflow" with numbered steps:
   - Step 1: `search(query="<topic>", limit=10)` — check what already exists; if near-duplicate title found, ask user: "Found existing note '<title>'. Create anyway or update existing?"
   - Step 2: If in an active session, skip context assembly (already oriented). Otherwise, call `agent_context(topic="<topic>", budget=4000)` for lightweight orientation
   - Step 3: For external sources: `ingest_source(title="<title>", content="<text>", input_kind="text", target_type="reference")` — creates a `captured` reference
   - Step 4: For synthesis/insights: `create_note(title="<synthesis title>", tags=["<domain/scope>"], session=<session_id if active>)` — creates note with session linking; reweave fires automatically via plugin
   - Step 5: Report: created IDs, link to the new content, any reweave suggestions from the create response, duplicate warnings from step 1
5. H2: "Content Type Decision" — brief guide (when to use which create tool):
   - Insight, idea, concept -> `create_note`
   - External article, paper, tool -> `ingest_source` (creates reference)
   - Follow-up action -> `create_task`
   - Quick idea, not ready to develop -> `garden_seed`
6. H2: "Anti-Patterns" — bullet list:
   - Do NOT call `reweave` manually after `create_note` — the Reweave plugin fires automatically; calling it manually causes double-reweave
   - Do NOT skip the search step — always check for existing content first
   - Do NOT use generic tags — use `domain/scope` format (e.g., `research/methodology`, not `research`)
7. Footer: "See `references/capture-workflow.md` for the full content type decision tree and tagging conventions."

**Create `plugin/skills/capture/references/capture-workflow.md`** (~60-80 lines):
1. H1: "Capture Workflow Reference"
2. H2: "Content Type Decision Tree" — expanded version of the decision tree from vault-methodology:
   - Is it an idea/concept/insight? -> `create_note`
   - Is it a decision with alternatives? -> `create_note` with `subtype="decision"`
   - Is it an external source? -> `ingest_source` with `target_type="reference"`
   - Is it a follow-up action? -> `create_task` with priority/impact/effort
   - Is it a quick seed? -> `garden_seed` (maturity=seed, low-ceremony)
3. H2: "Tagging Conventions" — explain domain/scope format:
   - Format: `domain/scope` (e.g., `math/algebra`, `python/stdlib`)
   - Single-segment tags get classified as `unscoped` — acceptable but less useful for filtering
   - Consistent tagging enables filtered search and cross-cutting discovery
4. H2: "Session Integration" — explain how capture works with sessions:
   - If a session is active, pass `session=<session_id>` to create calls
   - Session-linked content gets cross-session reweave on session close
   - If no session is active, content is still created but misses enrichment pipeline benefits

**Body** (~60-100 lines):

2. Opening paragraph: "Check any proposed decision or action against the vault's strategic priorities. Polaris is the vault's north star — this skill makes alignment checking a habit, not an afterthought."
3. H2: "Workflow" with numbered steps:
   - Step 1: Read `ztlctl://polaris` — load mission, priorities, and decision principles
   - Step 2: `check_alignment(decision="<proposed action or decision>")` — get `relevant_priorities` and alignment reasoning
   - Step 3: Present result:
     - If `relevant_priorities` is non-empty: "This decision aligns with [N] polaris priorities: [list priorities]. Reasoning: [alignment reasoning]."
     - If `relevant_priorities` is empty: "No direct priority overlap found. Current polaris priorities are: [list all]. Consider whether this is intentional scope expansion or a distraction."

4. H2: "When to Activate" — bullet list:
   - User asks "should I work on X?"
   - User asks "is this aligned with my priorities?"
   - User is about to start a new initiative or direction
   - User asks for a "polaris check" or "priority check"
5. H2: "Standalone Design" — one paragraph:
   - "This skill is standalone. Other skills (session, capture) may mention polaris in their workflows but do NOT invoke ztl:align. Each skill handles its own polaris checks independently. This prevents skill-chaining complexity."
6. Footer: "See `references/polaris-workflow.md` for details on polaris document structure and the alignment algorithm."

**Create `plugin/skills/align/references/polaris-workflow.md`** (~50-70 lines):

   - Mission statement (one sentence)
   - Priorities (ordered list, each with a description)
   - Decision principles (rules for breaking ties)
3. H2: "check_alignment Response" — what the tool returns:
   - `relevant_priorities`: list of priorities that match the proposed decision
   - `reasoning`: text explaining why the priorities match (or don't)
   - `alignment_score`: numeric score (if available)
4. H2: "Decision Audit Trail" — explain the optional decision note pattern:
   - Creating a `decision` subtype note after alignment check creates a permanent record
   - The note body should include: the decision, the alignment result, and the rationale
   - This builds a queryable history of strategic decisions over time
