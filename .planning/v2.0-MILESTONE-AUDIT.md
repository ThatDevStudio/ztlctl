### Unsatisfied (2/27)

#### PLUG-02: Pre-action hooks with modification and cancellation

**Phase:** 5 | **Plans:** 05-01, 05-03

`_dispatch_pre_action()` and `_dispatch_post_action()` are defined on `BaseController` (controllers/base.py lines 49, 84) and wired to `vault.plugin_manager`. However, **no concrete controller subclass calls them**. All 13 controllers delegate directly to services without invoking pre/post hooks.

**Impact:** Plugins implementing `pre_action` to modify kwargs or reject actions via `ActionRejection` will never receive the hook call. The pre/post-action hook system is dead code in production.

**Fix:** Each controller method must call `self._dispatch_pre_action(action_name, kwargs)` before service delegation and `self._dispatch_post_action(action_name, kwargs, result)` after.

#### PLUG-03: Plugin configuration via [plugins.\<name\>] sections

**Phase:** 5 | **Plans:** 05-01

`PluginManager.inject_configs()` (manager.py line 233) is defined and tested in isolation. However, `vault.init_event_bus()` never calls `pm.inject_configs(self._settings)`. Plugin `initialize()` and `get_config_schema()` hookspecs never fire during normal CLI or MCP startup.

**Impact:** Plugins that depend on TOML configuration will never receive their config. The entire plugin config pipeline is defined but never invoked.

**Fix:** Add `pm.inject_configs(self._settings)` after `pm.discover_and_load()` in `vault.init_event_bus()`.

### Partial (2/27)

#### AGNT-01: Structured error responses with recovery guidance

**Phase:** 6 | **Plans:** 06-01

Recovery guidance works correctly — `ServiceError.recovery` field + 36-entry `COMMON_ERROR_RECOVERY` + `from_result()` propagation. However, `McpError.detail` is not forwarded from `ServiceError.detail` in `from_result()`. Structured error context (e.g., which field failed, what value was invalid) is silently dropped.

**Fix:** One-line addition: `detail=result.error.detail` in `McpError()` construction in `response.py`.

#### AGNT-04: Progressive tool disclosure — category-based activation

**Phase:** 6 | **Plans:** 06-02

Category discovery works — `discover_categories`, `activate_category`, `deactivate_category` ActionDefinitions are wired. However, `generate_tools()` registers all 59 tools unconditionally. `_active_categories` state is advisory metadata only — agents can discover categories but cannot actually reduce the tool surface.

**Decision needed:** Either implement filtering in `generate_tools()` (requires dynamic re-registration) or clarify requirement as "category metadata/discovery" and accept as intentional design.

## Broken E2E Flows

### 1. Plugin pre_action rejection flow

```
1. User calls `ztlctl create note "My Note"`
2. CLI generator callback calls action.handler(vault, **kwargs)
3. Handler lambda constructs CreateController(vault).create_note(...)
4. CreateController.create_note() calls CreateService directly
5. ✗ MISSING: No call to _dispatch_pre_action("create_note", kwargs)
6. Plugin's pre_action hookimpl never fires
```

### 2. Plugin config injection flow

```
1. AppContext.vault → Vault(settings) → vault.init_event_bus()
2. pm.discover_and_load() loads plugins from entry points
3. ✗ MISSING: pm.inject_configs(self._settings) never called
4. Plugin get_config_schema() and initialize() never fire
5. Plugins depending on TOML config receive nothing
```
